# Remove Unused db-sync Cycle Repair

## Problem

`deps/db-sync/src/logseq/db_sync/cycle.cljs` implemented approximately 370 lines
of client-side DataScript repair for `:block/parent` and
`:logseq.property.class/extends` cycles. Its approximately 220-line unit test
namespace was the only consumer at decision time.

The client remote-apply path stopped requiring and calling `fix-cycle!` in
commit `905e131770` (`fix: no need to fix parent cycle for blocks`) on
2026-03-20. Current `frontend.worker.sync.apply-txs` repairs duplicate outliner
orders but has no cycle-repair call. Repository-wide searches find no other
production, script, documentation-contract, reflection, registry, or generated
source reference. The `@logseq/db-sync` package is private and does not export
the namespace as an external API. The remaining `deps/db-sync/.carve/ignore`
entry labeled `fix-cycle!` as an API, but it was a stale internal linter
exemption rather than an active package or runtime contract.

The unused utility therefore preserved a behavior model, transaction metadata,
and tests that were not part of runtime behavior. The implemented runtime guide
also had to carry a special warning explaining that the utility was not
integrated.

## Decision

The unused cycle repair implementation and its self-contained tests are removed:

- `deps/db-sync/src/logseq/db_sync/cycle.cljs`; and
- `deps/db-sync/test/logseq/db_sync/cycle_test.cljs`.

The obsolete `logseq.db-sync.cycle/fix-cycle!` API exemption and its comment are
removed from `deps/db-sync/.carve/ignore`.

The `Cycle repair utility` subsection is removed from
`docs/agent-guide/implemented/architecture/2026-08-24-logseq-runtime-and-engineering-guide.md`.
The runtime guide continues to describe the active duplicate-order repair where
relevant, without documenting a removed test-only implementation.

Do not change `frontend.worker.sync.apply-txs`, transaction application order,
outliner semantics, or server-side validation. Generated
`deps/db-sync/worker/dist/worker-test.js` is excluded from source edits and is
regenerated by the db-sync test build.

## Alternatives considered

### Reconnect `fix-cycle!` to remote apply

Rejected as a simplification because it would add cycle-repair transactions and
change synchronized graph behavior. If runtime evidence shows cycle repair is
needed, that work belongs to a separate bugfix or architecture decision with
new behavior tests.

### Keep the utility as a test-only design reference

Rejected because version control already preserves its history, while the
current source and test suite should describe executable behavior. Keeping it
also forces the runtime guide to distinguish implemented code from the active
path.

### Extract a generic graph-cycle library

Rejected because there is no second production consumer and the extraction
would relocate unused complexity instead of deleting it.

## Consequences

### Verification

- The cycle repair source and its self-contained unit test namespace are
  removed.
- Repository-wide search outside this decision record finds no
  `logseq.db-sync.cycle`, `cycle/fix-cycle!`, or equivalent build/test
  registration reference in tracked source.
- `deps/db-sync/.carve/ignore` no longer identifies the deleted `fix-cycle!`
  var as an API.
- `frontend.worker.sync.apply-txs` retains its current remote apply and
  duplicate-order repair behavior unchanged.
- The implemented runtime guide no longer documents the removed test-only
  utility or suggests that active client sync repairs reference cycles.
- `pnpm --dir deps/db-sync test` passes 188 tests with 4,101 assertions and
  regenerates its test bundle without the deleted namespace.
- `cd deps/db-sync && bb lint:carve` passes against the db-sync Carve
  configuration.
- `bb dev:lint-and-test` passes.

### Operational risks

- The deleted implementation includes algorithms for two kinds of cycles, so a
  future runtime bugfix cannot reuse it directly from the working tree. Its Git
  history and focused tests remain recoverable from commits before this
  decision.
- The removal assumes that the March 2026 production-path deletion was
  intentional for both supported attributes. Reintroducing any client-side
  repair would be behavior-changing and requires a new decision rather than a
  reversal hidden inside this simplification.
